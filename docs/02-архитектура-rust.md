# 02. Архитектура приложения на Rust

> Документ уровня «можно начинать кодить»: слои, крейты, модель данных, протокол,
> рендер-пайплайн, права, тестирование и структура репозитория.

---

## 1. Ключевое архитектурное решение: клиент-сервер в одном процессе

**Игра всегда клиент-серверная.** Даже в одиночной игре. У ГМа внутри приложения
запускается `GameServer` (tokio-таск), клиент ГМа подключается к нему через in-process
транспорт (`LocalTransport`). У игроков тот же `GameClient` подключается через
`NetworkTransport` (iroh).

```
┌────────────────────────── Приложение ГМа ──────────────────────────┐
│  UI (egui)          Renderer (wgpu)         Audio (kira)          │
│      │                   │                     │                  │
│      └──────────┬────────┴─────────────────────┘                  │
│                 ▼                                                 │
│           GameClient  ──intents──►  GameServer (authoritative)     │
│                 ▲                       │  │  │                   │
│                 └──── snapshots ────────┘  │  │                   │
│                                            │  │                   │
│                                    Storage │  │ AssetHost         │
│                                   (SQLite) │  │ (blake3 files)    │
│                                            ▼  ▼                   │
│                                    Transport (iroh / local)        │
└─────────────────────────────────┬─────────────────────────────────┘
                                  │ QUIC
                    ┌─────────────┴─────────────┐
                    ▼                           ▼
              Приложение игрока          Приложение игрока
              GameClient + UI            GameClient + UI
```

**Почему так.** Один код на ГМа и игрока; нет «двух правд»; автосейв, undo и лог действий
появляются сами; читерство невозможно; оффлайн-игра — просто локальный транспорт;
сетевой режим — единственное отличие.

**Правила:**
- Клиент **только отправляет намерения** (`Intent`) и **никогда не меняет состояние** напрямую.
- Сервер валидирует (права, лимиты), применяет, рассылает дельту.
- Клиент хранит «предсказанное» состояние для плавности (drag токена), но при конфликте
  побеждает сервер.

## 2. Слои и крейты (Cargo workspace)

```
vtt/
├── crates/
│   ├── vtt-core/        # домен: сущности, правила 5e, эффекты, дайсы. БЕЗ сети и UI
│   ├── vtt-proto/       # сообщения, версия протокола, serde/postcard
│   ├── vtt-server/      # авторитарный сервер: применение интентов, права, снапшоты
│   ├── vtt-net/         # транспорт: iroh, local, discovery (mDNS), диагност NAT
│   ├── vtt-store/       # SQLite, ассеты, манифесты, миграции
│   ├── vtt-render/      # wgpu: камера, спрайты, сетка, стены, туман, свет, эффекты
│   ├── vtt-ui/          # egui: панели, лист, чат, трекер, диалоги
│   ├── vtt-audio/       # kira/symphonia: музыка, эмбиент, звуки
│   ├── vtt-content/     # SRD 5.2, паки, импорт/экспорт, лицензии
│   ├── vtt-rules-5e/    # конкретная система правил (может быть плагином позже)
│   └── vtt-app/         # main: окно, DI-контейнер, сценарии запуска (GM/player)
└── tools/               # утилиты: импорт ассетов, генерация SRD-базы, бенчмарки
```

Зависимости строго вниз: `app → ui/render/audio → server → core`, `core` не зависит ни от чего
(кроме serde). Это позволяет тестировать правила без окна и сервера без сети.

## 3. Модель данных

Принцип: **данные — плоские документы с ID и версией, поведение — в правилах.**
Никакого наследования и «умных» объектов.

```rust
pub struct EntityId(pub u64);          // монотонный счётчик сервера + узел-источник
pub struct DocId(pub u64);             // версия документа для синхронизации

#[derive(Serialize, Deserialize)]
pub struct Actor {
    pub id: EntityId,
    pub name: String,
    pub kind: ActorKind,               // PlayerCharacter | Npc | Monster
    pub img: Option<AssetHash>,
    pub abilities: Abilities,          // str/dex/con/int/wis/cha
    pub prof: Proficiency,             // навыки, спасброски, экспертиза
    pub hp: HpBlock,                   // current/max/temp/hit_dice
    pub ac: u16, pub speed: Speed,
    pub attacks: Vec<Attack>,
    pub spells: Vec<SpellRef>,
    pub inventory: Vec<ItemRef>,
    pub effects: Vec<EffectInstance>,
    pub resources: BTreeMap<String, Counter>,   // ярость, ki, вдохновение...
    pub ruleset: RulesetId,            // "5e-2024"
}
```

Основные документы: `Campaign`, `Scene`, `Token`, `Actor`, `Item`, `Spell`, `Effect`,
`JournalEntry`, `Handout`, `RollTable`, `Playlist`, `Combat`, `User`, `Permission`.

**Сцена отдельно от токенов:** сцена содержит `tokens: Vec<Token>` (лёгкие),
`walls`, `lights`, `fog`, `templates`, `grid`, `map_hash`.

**Ассеты:** во всех документах только `AssetHash` (32 байта BLAKE3), никаких путей.

**Синхронизация:** у каждого документа `rev: u64`; сервер рассылает
`DocPatch { id, rev, fields }`. Полный снапшот — при подключении и при разрыве.

## 4. Модель правил (5e / 5.5e)

```rust
// Модификатор: «почему» и «сколько», чтобы UI мог объяснить
pub struct Modifier {
    pub source: ModSource,   // item, spell, condition, feat, dm
    pub target: ModTarget,   // AC, save(DEX), skill(Stealth), d20, speed, damage
    pub op: ModOp,           // Add, Set, Adv, Dis, Immune, Resist, Vulnerable
    pub value: i16,
    pub duration: Duration,  // rounds, until_turn_end, concentration
}
```

Принципы:
1. **Сумма модификаторов** — функция от активных эффектов, предметов и листа.
2. **Полуавтомат**: `resolve(attack) -> ProposedOutcome` — приложение показывает
   «попадание, 7 урона», ГМ жмёт «применить». Никаких автоприменений без кнопки.
3. **Объяснимость**: каждый итоговый бонус раскрывается в тултипе («+2 от ярости»).
4. **Данные, а не код**: правила 5e — таблицы/структуры; `vtt-rules-5e` их интерпретирует.
5. **Версионирование правил**: `ruleset: "5e-2014" | "5e-2024"` — выбор при создании кампании.

Парсер дайсов — отдельный крейт с тестами на `proptest`; DiceExpr → бросок → разбивка.

## 5. Протокол

```
Сообщение = { version: u16, kind: u16, id: u64, payload: postcard }
```

Каналы (QUIC streams):
1. **control** — join, snapshot, scene change, permissions (надёжно).
2. **state** — патчи документов (надёжно, с seq на документ).
3. **chat** — чат, броски, лог (надёжно).
4. **assets** — по стриму на файл, чанки 512 КБ, BLAKE3-проверка.
5. **datagrams** — движение токенов, курсоры, пинги (ненадёжно, 20–30 Гц).
6. **audio** — голос/музыка (в v1.1).

Интенты клиента (≤ 20 видов в MVP): `MoveToken`, `CreateToken`, `UpdateActor`,
`RollDice`, `SendChat`, `ChangeScene`, `RevealFog`, `SetInitiative`, `ApplyDamage`, `UseItem`, …

Сервер отвечает `Ack{n}` или `Deny{reason}` — клиент показывает понятную ошибку,
а не «ничего не произошло».

## 6. Рендер-пайплайн (wgpu)

Порядок проходов:
1. **Clear** → цвет сцены.
2. **Карта**: тайлы (если большая) или один квад; мипы; анизотропия.
3. **Сетка** — линиями (по батчу) или шейдером (лучше: `fract` координат, анизависимо).
4. **Слои объектов** — инстансинг: `{transform, uv, tint, layer, alpha}`.
5. **Стены/двери** — линии/полигоны, видимы только ГМу (полупрозрачно).
6. **Свет и туман**:
   - CPU: для каждого клиента считаем видимые полигоны (raycast по стенам, O(n log n));
   - рисуем `visibility_mask` в отдельную текстуру (полуразрешение достаточно);
   - в основном шейдере умножаем яркость: `lit * mask + ambient`, смягчаем края;
   - источники света — аддитивные круги с затуханием (уже с учётом маски).
7. **Шаблоны AoE, измерение, курсоры** — линии/полупрозрачные заливки.
8. **UI (egui)** — поверх, отдельным проходом.

Производительность: бюджет 8 мс на кадр при 4K-карте; туман пересчитывается только при
изменении стен/токенов/камеры (кэш), не каждый кадр. Целевой FPS — 120 (vsync 60).

## 7. Туман: гибридная модель

Три режима, как требует анализ конкурентов:
1. **Ручной** (кисть/полигоны) — P0.
2. **Память исследования** (auto-fog по токенам) — P1: полигоны раскрытого, хранятся в сцене.
3. **Динамический свет** — P1.

Внутри — единая модель `Visibility`:
```
revealed: Vec<Polygon>       // что уже видели (per-player)
current:  Vec<Polygon>       // что видят сейчас (по токенам игрока)
mask = revealed ∪ current    // то, что рисуется
```
Это дешевле клеточной модели Roll20 (та хранит до 50k клеток и «рвётся»).

## 8. Права и роли

```
Role = Gm | CoGm | Player | Spectator
Capability = View | Move | Edit | Delete
Target = Token(id) | Actor(id) | Scene(id) | Journal(id) | Asset(hash) | ServerSettings
```

Правило вычисления: `allow(role, capability, target)` + владение (`owner_id`).
Всё проверяется **на сервере**; клиенту лишь приходят `PermissionSet` для отрисовки UI
(«кнопка неактивна»), но полагаться на неё нельзя.

Спорные случаи (заложить сразу): игрок двигает свой токен; игрок видит чужой HP;
ГМ видит скрытые токены; зритель не видит ничего лишнего; co-ГМ всё, кроме смены пароля.

## 9. Расширяемость: WASM-плагины (P2, но заложить API)

- Плагин = `.wasm` + `manifest.json` (имя, автор, версия, **запрошенные права**).
- Хост: `wasmtime` (или `wasmi` — легче).
- API: чтение сцены (только разрешённое), отправка интентов (только разрешённые),
  свои панели (через декларативное описание, не HTML).
- Нет сети, нет файловой системы, нет доступа к памяти процесса.
- Подпись плагина ключом автора (ed25519) — по образцу Owlbear `Verified`.

Это ответ на боль Owlbear: «расширение = произвольный JS в вашей комнате без модели прав».

## 10. Хранилище и ассеты

```
%APPDATA%/VTT/
├── campaigns/<uuid>/campaign.db      # SQLite (сущности + метаданные)
├── campaigns/<uuid>/assets/ab/cd/<blake3>   # файлы
├── campaigns/<uuid>/manifest.json    # версия, лицензии, список паков
├── config.toml
└── logs/
```

- Импорт картинки: декод → ресайз до max 4096 → WebP q85 → BLAKE3 → запись.
- Миниатюры 256 px генерируются сразу (чтобы UI никогда не ждал).
- Бэкап: `campaign.vttpack` = zip(db + assets + manifest), zstd.
- Миграции схемы: `refinery` или свои `user_version`-скрипты.

## 11. Производительность: бюджеты

| Операция | Бюджет |
|---|---|
| Кадр | 8 мс (120 FPS) / 16 мс (60 FPS) |
| Пересчёт тумана | ≤ 4 мс, только при изменениях |
| Открытие сцены (кэш) | ≤ 100 мс |
| Применение интента на сервере | ≤ 1 мс |
| Рассылка дельты 8 клиентам | ≤ 2 мс |
| Поиск по компендиуму | ≤ 30 мс |
| Старт приложения | ≤ 1.5 с |

Правила: никакой аллокации в горячем цикле рендера, пулы для временных буферов,
`smallvec` где уместно, профилирование через `puffin`/`tracy`.

## 12. Тестирование

| Уровень | Инструмент | Что проверяем |
|---|---|---|
| Юнит | `cargo test` | парсер дайсов, модификаторы, CR-расчёт, права |
| Снапшоты | `insta` | сериализация документов, версии протокола |
| Свойства | `proptest` | парсер (`d20+5` не падает), сортировка инициативы |
| Интеграция | тест-харнес: сервер + 4 виртуальных клиента, локальный транспорт | синхронизация, конфликты, реконнект |
| Сеть | детерминированный симулятор потерь/задержек | толерантность к плохому каналу |
| Ручное | чек-лист сессии | 4 игрока + ГМ, 3 часа игры |

Отдельный «золотой» сценарий: создать кампанию → сцену → 5 токенов → бой 3 раунда →
сохранить → перезапустить → состояние совпадает. Это smoke-тест каждого релиза.

## 13. Структура работы над рендером (порядок)

1. Окно + wgpu + камера (пан/зум) + сетка.
2. Карта (одна текстура) + токены (инстансинг) + drag&drop.
3. Линейка, шаблоны, курсоры, пинг.
4. Ручной туман (маска).
5. Стены + полигональная видимость + свет.
6. Слои ГМ/фон/над токенами, скрытые токены.
7. Эффекты (частицы, ауры) — P2.

**Правило:** ни один пункт не начинается, пока предыдущий не работает в 60 FPS на
встроенной графике.
