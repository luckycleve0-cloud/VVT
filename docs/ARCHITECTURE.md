# Архитектура

Документ описывает, как устроен код сегодня, какие инварианты нельзя ломать и куда
встраивать следующие части (графику, UI, ассеты, P2P, плагины).

## 1. Граф зависимостей

```
                 ┌───────────────┐
                 │   vtt-app     │  CLI: demo / host / join / info
                 └───┬───┬───┬───┘
          ┌──────────┘   │   └──────────┐
          ▼              ▼              ▼
   ┌────────────┐  ┌───────────┐  ┌────────────┐
   │ vtt-server │  │  vtt-net  │  │ vtt-render │  окно (прототип)
   └─────┬──────┘  └─────┬─────┘  └─────┬──────┘
         │               │              │
         ▼               ▼              ▼
   ┌─────────────────────────────────────────┐
   │              vtt-proto                  │
   └──────────────────┬──────────────────────┘
                      ▼
                ┌────────────┐
                │  vtt-core  │
                └────────────┘
```

Правило: **зависимости идут только вниз**. `vtt-core` не знает ни про сеть, ни про
файлы, ни про время. Благодаря этому правила тестируются без окна и сервера.
`vtt-render` — лист: он ничего не решает и не меняет состояние, только рисует и
превращает ввод в `Intent`.

## 2. `vtt-core` — домен

| Модуль | Что внутри | Ключевые типы |
|---|---|---|
| `ids` | идентификаторы и генератор | `EntityId`, `PlayerId`, `IdGen` |
| `geom` | 2D-примитивы и пересечение отрезков | `Vec2`, `segments_intersect` |
| `grid` | сетка, снап, измерение дистанций | `Grid`, `GridKind`, `Measurement` |
| `dice` | парсер нотации и роллер | `DiceExpr`, `RollMode`, `RollResult` |
| `rules` | чистые формулы 5e | `ability_modifier`, `resolve_attack`, `adjust_damage` |
| `entities` | персонажи, эффекты, состояния, токены | `Actor`, `Token`, `Probe`, `Condition` |
| `scp` | лист персонажа SCP: 10 характеристик, 42 навыка, 9 классов, психоз | `ScpCharacter`, `ScpSkill`, `ScpClass`, `CheckResult` |
| `scene` | сцены, стены, свет, туман, шаблоны | `Scene`, `Wall`, `Fog`, `Template` |
| `visibility` | линия видимости, клетки, полигон | `can_see`, `visible_cells`, `visibility_polygon` |
| `combat` | трекер инициативы | `Combat`, `Combatant` |
| `permissions` | роли и права | `Role`, `Capability`, `can` |
| `content` | компендиум и поиск | `ContentRegistry`, `Spell`, `Monster` |
| `rng` | детерминированный PRNG | `Rng` |

`Probe` — важная деталь: любой расчёт возвращает итог **и** его расшифровку
(`+7 = Ловкость +3, Мастерство +3, Истощение −2`). UI показывает это в тултипе,
чтобы ГМ не спорил с приложением и мог поправить вручную.

## 3. `vtt-proto` — контракт

```rust
ClientMsg::Hello { name, code, protocol }
ClientMsg::Intent(Intent)     // MoveToken, CreateToken, DamageToken, Roll, Chat, …
ClientMsg::Ping { nonce }
ClientMsg::Bye

ServerMsg::Welcome(Welcome)
ServerMsg::Snapshot(Box<Snapshot>)
ServerMsg::Events(Vec<Event>)
ServerMsg::Denied { reason }
ServerMsg::Notice { text }
ServerMsg::Pong { nonce }
ServerMsg::Rejected { reason }
```

`PROTOCOL_VERSION` увеличивается при несовместимом изменении формы. Сервер отвечает
`Rejected` с понятным текстом — клиент не падает.

## 4. `vtt-server` — авторитет

- `Campaign` — сохраняемые данные (сцены, персонажи, бой, `next_entity_id`).
- `GameServer` — рантайм: подключённые клиенты, RNG, код комнаты.
- `handle(client, msg) -> Vec<Outgoing>` — единственная точка изменения состояния.
- `snapshot(client) -> Snapshot` — фильтрует скрытые токены под роль.

`Outgoing { to: Option<ClientId>, msg }`: `None` — всем, `Some` — одному.
Транспорт решает, как доставить; сервер не знает про TCP.

## 5. `vtt-net` — транспорт

- `codec` — фрейм `u32` длины (LE) + JSON, лимит 8 МБ.
- `tcp::TcpHub` — серверная сторона: accept-поток, по два потока на соединение,
  `poll()` / `send_to()` / `broadcast()`.
- `tcp::TcpClient` — клиент: писатель и читатель в отдельных потоках, `poll()` / `send()`.

## 6. Инварианты (нарушать нельзя)

1. **Состояние меняет только `GameServer::handle`.** Ни UI, ни транспорт.
2. **Права проверяются до применения**, а не в UI.
3. **Скрытые объекты не попадают в снапшот игрока.** Фильтрация — в `snapshot()`.
4. **RNG для бросков живёт на сервере.** Клиент не присылает результаты.
5. **Снап к сетке делает сервер.** Клиент присылает «куда хочу», сервер решает «куда можно».
6. **`next_entity_id` только растёт**, удалённые ID не переиспользуются.
7. **Протокол версионирован**; несовпадение — понятная ошибка, а не разбор мусора.

## 7. Как добавить новую возможность

### Новый интент (например, «повернуть токен»)

1. `vtt-proto`: добавить вариант в `Intent`, при необходимости — `Event`.
2. `vtt-server`: ветка в `apply_intent` — проверка прав через `permissions::can`.
3. `vtt-app/common.rs`: команда и `to_intent`.
4. Тест в `vtt-server/src/server.rs` (права + эффект) и, если сетевое, в
   `vtt-app/tests/tcp_session.rs`.
5. `PROTOCOL_VERSION` — только если ломается совместимость.

### Новое поле у сущности

1. Добавить поле **с `#[serde(default)]`**, если старые кампании должны читаться.
2. Если поле влияет на видимость — обязательно учесть в `snapshot()`.
3. Обновить `describe_event`/`print_snapshot`, если это видно пользователю.

### Окно и ввод (M2, прототип)

Крейт `vtt-render` — тонкий слой над `macroquad` (ADR-009). Устроен так, чтобы
рисование можно было заменить, не touching логику:

| Модуль | Что внутри | Зависит от окна |
|---|---|---|
| `camera` | `world_to_screen`, `screen_to_world`, `zoom_at`, `pan`, `fit` | нет (12 тестов) |
| `interact` | инструменты, перетаскивание, линейка, туман, пинги → `Action` | нет |
| `session` | `GameServer` + кампания + журнал + пинги; принимает `Intent` | нет |
| `sheet` | панель листа персонажа SCP: кнопки, броски, прокрутка навыков | нет логики — только действия |
| `draw` | отрисовка сцены и HUD | да (`macroquad`) |
| `main` (`vtt-play`) | окно, ввод, горячие клавиши, автосохранение | да |

Поток кадра:

```
ввод → Camera/Interaction → Action → LocalSession::apply(Intent)
     → GameServer::handle → Event → (журнал) → Scene (для отрисовки)
```

Окно **не меняет** сцену напрямую: всё идёт через `GameServer`, как и у сетевого
игрока. Поэтому одиночный режим и сетевой отличаются только транспортом.

Финальный рендерер (`wgpu` + `egui`) заменит `draw.rs` и главный цикл; `camera`,
`interact`, `session`, `vtt-proto` и `vtt-server` останутся.

### Ассеты

Транспорт скрыт за интерфейсом сообщений. План:

1. Ввести `trait Transport { fn poll(...); fn send(...); }` в `vtt-net`.
2. Добавить `IrohTransport` рядом с `TcpTransport` (feature-флаг `iroh`).
3. `vtt-app` выбирает транспорт по флагу CLI (`--transport tcp|iroh`).
4. Сообщения `ClientMsg`/`ServerMsg` не меняются — меняется только доставка.

Подробности и обоснование: [03-сеть-гм-хост.md](03-сеть-гм-хост.md).

### Ассеты

Сейчас `Scene::background` и `Token::image` — строки. Целевая модель:
`AssetHash(String)` = BLAKE3 содержимого, файлы в `assets/<aa>/<bb>/<hash>`,
манифест и ленивая подгрузка. Менять поле сразу на `AssetHash` стоит вместе с
появлением `vtt-store`, а не раньше.

### Плагины

Зарезервировано: плагины как WASM-модули с манифестом прав (чтение сцены, отправка
разрешённых интентов, свои панели). Ядро специально не даёт «скриптов на все случаи» —
иначе получится модель Owlbear, где расширение видит и меняет всё.

## 8. Тестирование

| Тесты | где | что |
|---|---|---|
| Юнит | `crates/*/src/*.rs` | дайсы, формулы, права, геометрия, камера, ввод |
| Интеграция транспорта | `vtt-app/tests/tcp_session.rs` | реальный TCP: подключение, снапшот, движение, скрытые токены, неверный код |
| CLI | `vtt-app/tests/cli_smoke.rs` | бинарник `vtt demo` проходит сценарий |
| Сценарий | `vtt demo` | живая документация и smoke-тест всего |

Окно проверяется вручную (запуск + горячие клавиши), потому что требует GPU и дисплея.
Логика окна (камера, ввод) покрыта юнит-тестами и от дисплея не зависит.

**Правило:** любой баг сначала воспроизводится тестом, потом чинится.

## 9. Производительность (текущие ориентиры)

Ядро headless, поэтому узкое место — сеть и будущий рендер.

| Операция | Бюджет | Как проверять |
|---|---|---|
| Применение интента | < 1 мс | бенчмарк на 500 токенах |
| Снапшот сцены | < 2 мс | `cargo bench` (появится) |
| Кадр рендера (будущее) | < 8 мс | puffin/tracy |

## 10. Чего в ядре намеренно нет

- потоков и `async` — этим занимается транспорт;
- файлового ввода-вывода — только `vtt-server::persist`;
- времени — все длительности передаются явно;
- глобального состояния и синглтонов;
- «умных» объектов с поведением — правила отдельно от данных.
