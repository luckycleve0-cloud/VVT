# 03. Сеть: ГМ как сервер — получится ли?

> Короткий ответ: **да, получится**, и это правильная архитектура для вашего случая.
> Но «как Hamachi» — это не одна технология, а лестница из четырёх режимов, и
> 100%-й гарантии «просто работает» без единого сервера в интернете не существует.
> Ниже — честная механика, цифры и что именно надо построить.

---

## 1. Почему идея верна

| Критерий | Облачный сервер (Roll20) | ГМ-хост (наш вариант) |
|---|---|---|
| Стоимость | $X/мес за каждого ГМа | **0** (релей — копейки и только при неудаче) |
| Задержка | зависит от расстояния до ДЦ | **минимальная** (напрямую, часто LAN/город) |
| Приватность | данные у вендора | **данные у ГМа** |
| Работа без интернета | нет | **да, LAN** |
| Владение контентом | лицензия подписки | **файлы у пользователя** |
| Риск | вендор закрылся — всё пропало | нет вендора |
| Сложность | низкая у клиента | **высокая у нас** (это цена) |

Именно так уже работают Foundry VTT (self-hosted), Fantasy Grounds (LAN/Direct) и MapTool.
Так что это не экзотика, а проверенная модель — просто у всех трёх **боль**: настройка
проброса портов. Наша задача — съесть эту боль.

---

## 2. Почему «просто подключиться» не всегда работает: NAT

Домашний роутер даёт компьютеру «серый» адрес (`192.168.x.x`). Снаружи виден только
публичный IP роутера, и входящие соединения он по умолчанию не пропускает.
Игрок не может «позвонить» на ПК ГМа, пока роутер не согласится пропустить пакет.

Четыре уровня проблемы:

| Ситуация | Доля (оценка) | Решение |
|---|---|---|
| ПК ГМа в одной сети с игроками (LAN) | ~5% сессий | mDNS/broadcast-обнаружение, 0 действий |
| Роутер с UPnP/NAT-PMP/PCP (обычный домашний) | ~60–75% | приложение само просит роутер открыть порт |
| Роутер без UPnP, но с пробросом вручную | ~15–25% | инструкция-визард «откройте порт», 1 раз |
| **CGNAT / симметричный NAT / мобильный интернет / общага** | ~10–20% | **только релей или VPN** |

**CGNAT** — главный враг: провайдер выдаёт один публичный IP на сотни абонентов,
порт пробросить физически нельзя. У мобильных операторов и в общежитиях это норма.
Без релея такие игроки не подключатся никогда.

Отсюда вывод: **релей обязателен как fallback**, но он не должен быть «сервером игры» —
только транспортом для трафика, который не смог пройти напрямую.

## 3. Лестница режимов: от лучшего к запасному

```
[1] LAN            mDNS-обнаружение, прямой сокет       0 действий, 0 задержки
      ↓ не нашли
[2] Direct + UPnP  приложение открывает порт на роутере  0 действий (если роутер умеет)
      ↓ не вышло
[3] Hole punching  STUN + обмен кандидатами через лобби 0 действий, P2P-канал
      ↓ не вышло (CGNAT/симметричный NAT)
[4] Relay          трафик через маленький релей        0 действий, +20–80 мс
      ↓ полный провал сети
[5] Manual         ручной IP:порт / VPN (Radmin, ZeroTier, Tailscale)
```

Все пять режимов используют **один и тот же протокол** — меняется только транспорт.
Это важно: игровая логика не знает, как её трафик доехал.

### 3.1. Что даёт каждая технология

| Технология | Что делает | Зрелость | Где брать в Rust |
|---|---|---|---|
| **mDNS** | обнаружение ГМа в локальной сети | зрелая | `mdns-sd` |
| **UPnP IGD / NAT-PMP / PCP** | авто-проброс UDP-порта | работает на 60–80% роутеров, иногда «тихо» ломается | `igd-next`, `natpmp` |
| **STUN** | узнаём свой внешний IP:порт, тип NAT | зрелая | `stun` / через `webrtc` |
| **ICE / hole punching** | пробиваем NAT с двух сторон | зрелая, но не 100% | `webrtc` (webrtc-rs), `str0m`; или готовое — `iroh` |
| **QUIC (RFC 9000)** | надёжные стримы + датаграммы по UDP, TLS 1.3 внутри | зрелая | `quinn`, `iroh` |
| **TURN** | релей-сервер (простой, дорогой по трафику) | зрелая | `webrtc` / свой на QUIC |
| **DERP-подобный релей** | релей с мультиплексированием, дешевле TURN | зрелая (Tailscale) | `iroh` (встроен) |
| **WireGuard-подобный VPN** | «как Hamachi»: виртуальная LAN | зрелая | `boringtun`, `wireguard-rs` (сложно) |

### 3.2. Рекомендация: `iroh`

Для Rust в 2026 есть почти готовое решение — **iroh** (проект n0-computer, версия 1.x).
Он даёт ровно ту лестницу, которую мы нарисовали:

- QUIC-соединения по «NodeId» (публичный ключ), а не по IP;
- автоматический hole punching через STUN-подобный механизм;
- **встроенный релей** на случай, если пробить не удалось (трафик шифруется end-to-end,
  релей видит только шифротекст);
- «tickets» — строки, которые и есть наш инвайт-код;
- работает и в LAN (через mDNS), и через интернет.

Это снимает 80% работы по NAT traversal. Что остаётся нам: свой сервер-«лобби»
(маленький, дешёвый) и поддержка ручного режима.

**Альтернатива без зависимости от iroh:** `quinn` + свой STUN + свой релей.
Больше контроля, на 2–3 месяца больше работы, и всё равно нужен релей-сервер.

## 4. Роль маленького сервера (лобби/сигналинг)

Полностью без сервера в интернете — нельзя (кто-то должен свести ГМа и игроков,
если они не в одной сети). Но этот сервер **не хранит игру**:

| Что хранит | Объём | Зачем |
|---|---|---|
| `room_id → host_node_id, ticket, expiry` | байты | чтобы игрок по коду нашёл ГМа |
| Список кандидатов (IP:port) на время handshake | КБ | hole punching |
| Релей-маршрутизация | нет состояния (stateless) | пропуск трафика |

Стоимость: **почти ноль**. Cloudflare Workers free tier (100k запросов/день) или
маленький VPS за €4/мес — хватит на тысячи сессий. Релей по трафику: типичная сессия
6 игроков без голоса — 50–300 МБ; с голосом — 1–2 ГБ. При €0.01/ГБ это €0.02 за сессию.

> Важно: релей нужен только тем ~10–20% игроков, у кого не пробился NAT. Если хостить
> релей самому на VPS с безлимитом (Hetzner), расходы фиксированные и смешные.

## 5. Как это выглядит для пользователя

1. ГМ жмёт «Создать комнату» → приложение поднимает сервер, пробует UPnP, регистрируется в лобби.
2. Появляется **код `K7M2Q9`** и ссылка `vtt://join/K7M2Q9` (плюс QR для телефона).
3. Игрок вводит код → приложение получает тикет → пробует LAN → direct → punch → relay.
4. В лобби видно: кто подключён, каким путём (LAN/direct/relay), пинг.
5. Если что-то не так — встроенный «Диагност»: показывает тип NAT, открыт ли порт, что делать.

Всё остальное — как в Hamachi/Radmin, но **без установки второго приложения** и без
виртуального сетевого адаптера.

## 6. Передача контента с ПК ГМа (ассеты)

Это второй по важности пункт после NAT: «у игроков есть все токены, потому что ГМ их передаёт».

### 6.1. Content-addressed хранилище

- Каждый файл получает `hash = BLAKE3(contents)`.
- В состоянии игры лежат **только хэши**, не пути и не картинки.
- Клиент, увидев незнакомый хэш, просит его у ГМа; получив — проверяет хэш и кэширует навсегда.
- Одинаковые картинки (один и тот же токен 20 раз) передаются один раз.

### 6.2. Что и сколько весит

| Контент | Типичный вес | Когда передаётся |
|---|---|---|
| Карта сцены (4K WebP q80) | 1.5–4 МБ | при открытии сцены |
| Карта 8K | 6–15 МБ | при открытии, тайлами |
| Токен/портрет (512px WebP) | 40–150 КБ | при появлении |
| Превью-миниатюры | 3–10 КБ | **сразу** (чтобы UI не ждал) |
| Статблок/лист (данные) | КБ | сразу |
| Музыка | стриминг Opus 96–128 кбит/с | потоком |

**Первое подключение к сессии:** 15–40 МБ на игрока. При 6 игроках ГМ отдаёт
100–240 МБ. На канале 10 Мбит/с это ~3 минуты (параллельно, с прогрессом) — нормально.
На ADSL 1 Мбит/с — 20+ минут: поэтому **обязательна переупаковка на стороне ГМа**
(WebP, ограничение 4096px, миниатюры сначала) и предзагрузка «следующей сцены» в фоне.

### 6.3. Как передавать

- Отдельный **QUIC-стрим на каждый ассет** → параллельно, без блокировки игрового состояния.
- Чанки по 256 КБ–1 МБ, докачка после обрыва, `BLAKE3` проверка.
- Игровое состояние (ход, чат) идёт в **отдельном стриме с приоритетом** — чтобы
  загрузка карты не лагала чат (head-of-line blocking в QUIC решается стримами).
- Движение токенов — **ненадёжные датаграммы** (потеря пакета не критична, интерполируем).

### 6.4. Музыка и голос

- Голос: Opus 48 кГц, mono, 24–32 кбит/с на игрока. Сервер (ГМ) микширует/ретранслирует.
  ГМ отдаёт ~6×32 = 190 кбит/с ≈ 1.4 МБ/мин.
- Музыка: один поток Opus 96–128 кбит/с, **не отдельный на каждого** — multicast-рассылка
  одного закодированного потока. 128 кбит/с = 16 КБ/с ≈ 58 МБ/час.
- Итого с голосом и музыкой: **~40 КБ/с исходящего** у ГМа. Любой современный интернет тянет.

## 7. Синхронизация состояния

Модель: **авторитарный сервер** (ГМ). Никакого CRDT — он нужен для совместного
редактирования без сервера, а у нас сервер есть.

| Что | Как | Частота |
|---|---|---|
| Позиция токена при перетаскивании | датаграмма `{token, x, y, seq}` | 20–30 Гц, интерполяция на клиенте |
| Изменение состояния (HP, статус) | надёжное сообщение-«интент» → сервер валидирует → рассылка дельты | по событию |
| Полный снапшот | при подключении / рассинхроне | редко |
| Порядок | `seq` на сущность, отбрасываем старые | — |
| Права | **только сервер** решает, можно ли; клиент не авторитетен | всегда |

Клиент — «тонкий»: он отправляет намерения (`move token 5 to (x,y)`, `roll 1d20+3`),
сервер применяет и рассылает результат. Это же даёт бесплатно: автосейв, undo,
лог действий и невозможность читерства.

---

## 8. Безопасность

| Угроза | Мера |
|---|---|
| Подделка ходов/бросков | сервер авторитетен, клиент не может писать состояние напрямую |
| Мусор/DoS от клиента | лимиты размеров сообщений (1 МБ), rate limit (100 сообщ./с), лимит ассетов |
| Path traversal при загрузке ассетов | имена файлов = только хэш, никаких путей от клиента |
| Исполнение контента | в контенте **нет кода**; плагины (когда будут) — WASM в песочнице |
| Перехват трафика | QUIC = TLS 1.3 всегда; MITM исключён |
| Подмена ГМа по коду комнаты | тикет = `room_id + node_id(public key) + expiry`; короткий код бессмысленен без ключа |
| Сертификаты | самоподписанный сертификат + **pinning по ключу из инвайта** (как SSH known_hosts), либо raw public keys (RFC 7250) |
| Слив IP | ГМ видит IP игроков (и наоборот) — это неизбежно в P2P; предупреждение в UI |
| Кража кампании | опциональный пароль на «экспорт кампании» (P2) |

**Права (permission model):** роль (GM / co-GM / player / spectator) × объект
(token / scene / journal / actor / asset) × действие (view / move / edit / delete).
По умолчанию: игрок двигает только свои токены, редактирует только свой лист,
видит только разрешённые статьи журнала.

## 10. Сценарии: «что нужно от игрока/ГМа»

| Сеть | Режим | Действия пользователя | Работает |
|---|---|---|---|
| Все в одной квартире/LAN | mDNS | **0** | ✅ |
| Домашний роутер с UPnP | Direct | **0** | ✅ (60–80%) |
| Домашний роутер без UPnP | Direct + проброс | 1 раз настроить порт (визард) | ✅ |
| CGNAT / мобильный интернет | Relay | **0** | ✅ (+20–80 мс) |
| Корпоративный/учебный firewall | Relay (443/TCP) | **0** | ✅, но может резаться |
| Нет интернета вообще | LAN | **0** | ✅ |
| Роутер «злой» и релей заблокирован | VPN (Radmin/ZeroTier) | поставить VPN | ✅ (последний рубеж) |

Оценка: **85–95% сессий** проходят без единого действия пользователя.
Остальные — с релеем (тоже без действий) или с VPN (1 раз поставить).

---

## 11. Что НЕ надо делать

- ❌ Свой VPN-адаптер (TAP/TUN, драйверы на Windows, антивирусы) — Hamachi-путь, боль, синие экраны.
- ❌ Только TCP — плохо для realtime, head-of-line блокировки.
- ❌ Только облако — теряется вся идея.
- ❌ Свой протокол шифрования — только TLS 1.3/QUIC.
- ❌ Хранить игру на сервере лобби — приватность и стоимость.
- ❌ Гарантировать «100% подключение» в маркетинге — релей решает, но честнее сказать «в 9 из 10 случаев напрямую».

## 12. Итоговый вердикт

1. **Технически реализуемо полностью.** Никаких непреодолимых препятствий нет; всё
   уже работает в Foundry (self-host) и частично в iroh/Tailscale.
2. **Ключевой риск — не технология, а UX вокруг неё.** Если игрок увидит «пробросьте порт»,
   он уйдёт в Roll20. Поэтому лестница режимов + авто-релей + визард диагностики — это
   не «дополнительная фича», а **ядро продукта**.
3. **Стоимость инфраструктуры: ~0–10 $/мес** на старте, при росте — пропорционально
   только релейному трафику.
4. **Задержка лучше, чем у облачных VTT** в большинстве сценариев (напрямую, без ДЦ).
5. **Главный компромисс:** ГМ должен держать приложение открытым; если он закрыл ноутбук —
   игра останавливается. Лечится снапшотами и «передачей хоста» (P2), но не в MVP.

> **Ответ на вопрос «получится ли»: да. Делать можно. Но 2–3 месяца из 6 уйдёт именно
> на сеть и на то, чтобы она выглядела как «просто работает».**

## Приложение. Схема протокола (черновик)

```
QUIC connection (TLS 1.3, ALPN "vtt/1")
├── stream 0 (control, reliable, ordered)
│     JOIN, LEAVE, PERMISSION, SCENE_CHANGE, SNAPSHOT_REQ
├── stream N (assets, reliable, per-asset)
│     ASSET_REQ{hash} → ASSET_CHUNK{hash, idx, bytes} → ASSET_END{hash}
├── datagram (unreliable)
│     TOKEN_MOVE{token, x, y, seq}, CURSOR{player, x, y}, PING{player, x, y}
├── stream M (chat, reliable)
│     CHAT{from, text, visibility}, ROLL{expr, result, visibility}
└── stream A (audio, reliable-low-latency)
      VOICE{player, opus_frame}, MUSIC{opus_frame}
```

Каждое сообщение: `{ type: u16, id: u64, seq: u32, payload: bincode }`.
Версия протокола в handshake; несовпадение — понятная ошибка «обновите приложение».
